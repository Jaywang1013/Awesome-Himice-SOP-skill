# 用印申请 · 业务口径硬规则

> 每条标来源与日期。**口径冲突时以财务/合规最新说法为准**，并回改本文件。
> 本文件的每条规则都必须在 `SKILL.md` 的「提交前验证清单」里有对应动作，不能只躺在这里。

## BR-01 文件管控分类怎么定

- **规则**：三选一 —— `对客销售合同`（与客户签署的合同、PO单、客户采购订单）、`投标文件`（标书、报价单、设计方案、投标授权书、投标入库文件等）、`对供应商采购`（与供应商签署的采购合同）。由**用户口头告知**，不由执行方自行判断。
- **为什么**：分类决定合规路径与后续归档，判错要走回头流程。
- **验证动作**：提交前清单「文件管控分类与用户告知一致」；用户给的简写（对客合同／供应商合同／投标）需映射到表单正式选项值。
- **来源**：用户 2026-10-22 说明；表单选项实测 2026-10-22。**以合规部最新分类说明为准。**

## BR-02 跨公司使用集团（海口）印章：两个必须当场问的确认项

- **规则**：该栏选 **是** 时，必须当场向用户确认两项，**不取默认值**：
  1. **电子印章 / 实体章**
  2. **是否需要原件**
- **附加口径**：该栏选「是」后，**「所用公司印章」栏不需要跟着改成集团**，仍填申请人所在公司。
- **为什么**：集团对跨公司用印有独立规定；是否需要原件涉及合同原件邮寄集团法务归档。
- **验证动作**：提交前清单「跨公司印章选择正确；若为『是』，电子章/实体章与是否需要原件已问过用户」。
- **来源**：用户 2026-10-22 说明。

## BR-03 文件份数：上传份数 ≠ 盖章份数

- **规则**：「文件份数」填**用户上传的文件份数**，不是合同约定的盖章份数。
- **为什么**：合同常写「一式贰份，甲乙双方各执壹份」，但表单问的是上传了几份文件。两者含义不同，极易混淆。
- **验证动作**：提交前清单「文件份数与实际上传份数一致」；当合同条款的份数与上传份数不一致时，**向用户确认**后再填，不自行取舍。
- **来源**：用户 2026-10-22 确认（当时合同写「一式贰份」，用户确认填 1）。

## BR-04 用印文件名称的构成

- **规则**：`鱼鹰编号 + 项目名称 + 文件名称` 三段拼接；**「文件名称」就是用户上传文件的原名**，不重命名。
- **附加口径**：鱼鹰编号可带前缀（如 `(厦门)XK...`）；项目名称用全称，**不用简称**。
- **验证动作**：提交前清单「用印文件名称 = 鱼鹰号 + 项目名称 + 上传文件名，且与附件文件名一致」。
- **来源**：用户 2026-10-22 说明。

## BR-05 归档：按项目分，同项目不重复建文件夹

- **规则**：归档到 `用印流程-{鱼鹰号}-{项目名称}/`，内含 `合同原件/`、`提交凭证/`、`归档台账.md`。**同一项目的多次用印放同一个文件夹**。
- **台账字段**：日期 / 文件名与份数 / 印章类型（电子章·实体章）/ 接收单位 / 提交人 / 当前状态 / 备注；缺件显式写「xx 后补」。
- **状态栏硬规则**：必须写清来源——**谁提交的、依据是用户告知还是截图**。审批单截图或链接**向用户索取，不得编造**。
- **验证动作**：本规则属**提交后阶段硬规则**，动作落在「归档」一节（不在提交前验证清单内）：台账状态栏含来源标注；截图缺失则写「后补」。
- **来源**：用户 2026-10-23 定（原规则 2026-10-22）；Chief 2026-10-23 补充状态栏来源要求。

## BR-06 提交动作由用户完成

- **规则**：执行方填完单、核对完，**停在提交前**，由用户在钉钉点提交（或用户明确说「提交」后执行方代点）。
- **为什么**：提交后撤回需人工，机器人不自动撤回。
- **验证动作**：提交前清单全部通过 + 用户明确确认，二者同时满足才允许点提交。
- **来源**：Chief 2026-10-23 明确；用户 2026-10-23 曾自行提交。

## BR-07 金额与接收单位不臆造

- **规则**：合同金额、文件接收单位、份数一律从合同读出；读不出就问用户，**绝不臆造**。缺件要显式告知，不静默提交。
- **验证动作**：提交前清单「合同金额与合同条款一致，且汉字大写自动生成结果正确」「文件接收单位是合同对方单位全称」。
- **来源**：用户 2026-10-22 说明；Chief 2026-10-23 强调（合同金额、条款、印章类型一律不臆造）。
